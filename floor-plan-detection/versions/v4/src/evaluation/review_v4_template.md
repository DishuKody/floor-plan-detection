# v4: accurate shape boundaries on simple (raster) plans, complex plans unchanged

Versions are preserved side by side: `versions/v1`, `v2`, `v3` (the implementation before this work, including its raster outputs `versions/v3/raster_output*`) and the current v4 (`src/`, `config/`).
Every number below is generated by `python -m src.evaluation.run_v4_evaluation` (-> `evaluation_v4/summary.md|json`, this file via `python -m src.evaluation.make_review_v4`) or checked by the test-suite (58 tests); none are typed from memory.

## 1. What `expected.png` is, and is not
It is a 644 x 898 **screenshot of the v3 overlay of `floor_plan.pdf` with hand-drawn red marks**, not a clean ground-truth mask:
* **13 thick straight red lines** (3-5 px) mark where a room boundary is expected: wall faces and door / opening thresholds (bedroom doors, the dining room's top and bottom edges, the kitchen top, the tops of the two WCs, the bottom of bedroom 1, ...). Two of them (at the store door and below the corridor) are drawn **slanted** by hand.
* **2 large red X's** over the title text "TYPICAL FLOOR PLAN" and the logo "ID 13501" mean "these are not shapes".
* Our own red review rings and door dots are also in the screenshot; they are small (< 60 px area) and are discarded by size.

It is **sparse**: it says where boundaries should be at 13 places, not everywhere. So the **recall of those lines is measurable, precision is not**. The screenshot is registered to our full-page output with SIFT + RANSAC affine ({n_inl} inliers, RMS {rms} px, uniform scale {sc}); the reference file is never modified.

## 2. Root causes found in v3 (before changing anything)
Evidence: v3 detected boundaries (blue) over the expected lines (red), full page: `evaluation_v4/expected_comparison/v3/`.
1. **Text became wall.** Bold glyphs survive the wall-thickness filter, which produced holes and wiggly outlines inside rooms ("Bath", "Store", "Cupboard", "Dining 18.3 m2") and **false rooms on the title and logo**, which is what the X marks mean (they covered {x30} and {x31} of the marked regions).
2. **The plan outline was built from all ink (text included)**, so the title / logo box fell inside it.
3. **Doors and openings were never closed**, so rooms were split by a geodesic (curved) label-proximity partition instead of the straight wall / threshold line (dining room, kitchen, bedroom doors).
4. An elliptical opening rounded wall corners; polygons were taken half a pixel inside the mask; there was no axis snapping.
5. Labels outside the outline (the dashed-outline kitchen veranda) are dropped once the outline is fixed.

## 3. Changes (generic: no per-PDF constants; thresholds are fractions of the image width)
| change | where |
|---|---|
| all OCR text is removed from the wall mask (glyph blobs inside text boxes; walls passing under a label are kept) | `raster/segmentation.thick_walls` |
| square-kernel opening keeps wall corners exact; Otsu with a fallback for binary images (Otsu returns 0 on a pure 0/255 image, giving an empty mask) | same |
| plan outline = hull of the **wall cluster** plus large thin outlines *attached* to walls; padded before closing (OpenCV treats the image border as set and fused walls near the edge into a frame) | `plan_footprint` |
| **wall-end extension**: every skeleton end extends along its own axis to the next wall (<= 0.11 W to any wall; <= 0.27 W only at another wall end or corner); parallel walls are never bridged; the ray starts at the true half-thickness (my first version started inside the wall and logged gap 0) | `close_wall_gaps` |
| enclosed free-space components are the rooms; label-proximity splitting only inside open-plan components (flagged) | `segment_rooms` |
| labels outside the outline (dashed veranda) are bounded by the thin outline with dash gaps bridged, flagged | `segment_rooms` |
| unlabelled spaces whose boundary is mostly outline hull (exterior recesses) are not reported; walled-in closets are | same |
| pixel-exact polygons (half-pixel push-out, 0.8 px simplification), holes of at least 150 px^2 kept, near-axis edges snapped exactly | `mask_to_polygon`, `postprocessing/shapes.snap_axis_aligned` |
| shape descriptors for **all** rooms (raster and vector): circle / square / rectangle / rectilinear_polygon / irregular_polygon, rectangularity, solidity, circularity, axis-aligned edge fraction | `postprocessing/shapes.describe` |
| circular shapes (basins, columns) by Hough plus closed-ring verification; wall extensions exported as `opening_line` elements | `raster/pipeline_raster` |
| explicit coordinate chain image px <-> PDF pt <-> page px (`PageTransform`), all three stored per room | `segmentation.PageTransform` |

Convention: a virtual boundary across a door opening runs on the **wall centreline** (the user's lines are drawn there, and two rooms sharing a doorway then share one straight boundary), so each room outline has a shallow half-slab recess at its doorways; real wall faces keep face boundaries.

### 4.3 Synthetic ground truth (tests)
A synthetic plan with exactly known rooms: IoU >= 0.985 and Hausdorff <= 2.5 px for every room, no holes from bold text, door openings closed by straight lines, parallel walls never bridged, title and logo not a room. A synthetic PDF with the image embedded at a known rectangle: every room lands within 2 pt (IoU >= 0.97) of its true rectangle **in PDF points**.

### 4.4 Complex plan (Student Accomodation.pdf): no degradation
v3 -> v4: rooms {vr_old} -> {vr_new}, same type {vr_type}, **min IoU {vr_iou}**, max vertex displacement **{vr_disp} pt**, elements identical ({vr_el}). The vector path is untouched except that rooms now also carry shape descriptors. Adaptive selection: no vector geometry plus an embedded image selects the raster mode; otherwise the vector mode runs.

### 4.5 Full page, coordinates, runtime
* The overlay, mask and reference render are exactly the page render (same size and aspect). Outside painted rooms, elements and legend the overlay is pixel-identical to the plain render, for the vector and the raster outputs (tests).
* image px, PDF pt and page px agree to 0.06 px; polygons are valid; there are no text-induced holes.
* Runtime on the GPU in this session: floor_plan {t1} s, floor_plan2 {t2} s, Student {t3} s; peak RAM {ram1} / {ram2} / {ram3} MB.
* GPU vs the CPU-only environment (interleaved, 3 rounds, identical outputs): floor_plan pipeline x1.34 (OCR x2.74, process wall x1.22); floor_plan2 x1.13 (OCR x2.40, process wall x1.03, i.e. break-even for such a small plan). Sampled: peak VRAM 1.78 / 1.71 GB (+1.2 GB), peak utilisation 92-96 %, mean about 29 % (`evaluation_v4/benchmark_cpu_vs_gpu/`). Only OCR (ONNX CUDA) and the symbol template matching use the GPU; the segmentation is classical OpenCV on the CPU, where a GPU would not help.

## 5. Tried and rejected (measured against the same reference)
* Removing small thick blobs (fixtures) from the wall mask: slightly **worse** (mean 5.75 -> 5.94 px) because it removed a cooker block that is a valid extension target; off by default (`min_wall_len_k: 0`).
* Terminating extensions at a perpendicular wall's corner: **no effect** on these plans (kept, harmless).
* Full-wall-thickness closures (boundary on the wall face): **worse** against the user's lines (mean 5.4 -> 7.1 px, recall@4 62 % -> 34 %); hence the centreline convention.
* A hull from elliptical closing: curved porch and recess artefacts; replaced by a square kernel. Dropping every unlabelled space that touches the hull lost the second WC; replaced by the wall-versus-hull boundary test.

## 6. Remaining limitations
* **Slanted hand-drawn lines** (2 of 13) are not reproduced; the extension is axis-aligned (`rectilinear_walls: false` allows other directions but was not evaluated).
* **Open-plan areas** (entrance, living room and corridor have no walls between them) are still split midway between labels: curved boundaries, flagged `open_plan_split_by_label_proximity`; 14-18 % of boundary length is in free space.
* The second WC of `floor_plan.pdf` is unreadable to OCR and is reported as `unknown`; a sink unit in `floor_plan2.pdf` is reported as an `unknown` enclosed shape (it is a thick closed outline). Text suppression depends on OCR boxes: bold text that OCR misses would still become wall.
* Circle detection is not precise: it finds basins and veranda columns but also two oversized circles in the second WC.
* The kitchen veranda is bounded by a dashed line, not a wall (flagged).
* **No full ground truth**: only 13 hand-drawn lines plus the printed room areas exist. Thresholds such as `door_gap_frac` and `pair_gap_frac` were chosen from the plan geometry, with `expected.png` in the loop for the ablations above, so some fit to this one reference is possible. `floor_plan2.pdf` and the synthetic plans are the checks that are independent of it.
* Vector mode: rooms are derived from a 4 px/pt raster of the vector walls (0.25 pt), not from exact vector polygons; unchanged here.

## 7. Reproduce
```powershell
cd floor-plan-detection
.venv\Scripts\python.exe -m src.evaluation.run_v4_evaluation      # runs all 3 PDFs, compares with v3 and expected.png, writes evaluation_v4/
.venv\Scripts\python.exe -m src.evaluation.make_review_v4         # regenerates this document from evaluation_v4/summary.json
.venv\Scripts\python.exe -m pytest tests -q                       # 58 tests
..\run.bat "..\floor_plan.pdf" "..\output"                        # one PDF -> overlay / masks / rooms.json / elements.json
.venv\Scripts\python.exe -m src.evaluation.expected_ref ..\expected.png ..\output "v4" evaluation_v4\mine     # expected.png metrics + full-page images for any output folder
.venv\Scripts\python.exe -m src.evaluation.benchmark_device "..\floor_plan.pdf" bench --rounds 3             # CPU vs GPU (needs .venv_cpuref)
```
